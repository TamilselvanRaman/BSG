BSG FULL IMPLEMENTATION PLAN Phase-by-Phase Product,
UI/UX, Flutter, Backend and Release Roadmap

DOCUMENT PURPOSE This document is the implementation blueprint for CLICK
SMART CHART. It defines the product structure, visual system, technology
stack, page-by-page delivery sequence, business workflows, data rules,
testing gates and release plan. Build one phase at a time. Do not
generate all screens in one coding task.

============================================================ 1. PRODUCT
DEFINITION AND TERMINOLOGY
============================================================

Application: BSG Platform: Android mobile application
(Flutter) Primary purpose: Manage incoming lots, suppliers, customers,
cash bills, credit bills, payments, expenses, stock and business
reports.

MANDATORY TERMINOLOGY - Seller becomes Supplier. - Buyer becomes
Customer. - Seller List becomes Supplier List. - Buyer List becomes
Customer List. - Seller Ledger becomes Supplier Ledger. - Buyer Ledger
becomes Customer Ledger.

Apply these terms consistently in screen titles, buttons, forms,
filters, reports, PDF bills, notifications, API labels and user-facing
messages. Do not rename unrelated accounting terms without business
approval.

PRIMARY BOTTOM NAVIGATION 1. Home 2. Bills 3. Expenses 4. Users 5.
Reports

HOME QUICK ACTIONS 1. Create Cash Bill 2. Create Credit Bill 3. Received
Amount 4. Create Lot 5. Users

The five Home actions are shortcuts into the same workflows accessible
from the relevant navigation sections. Do not create duplicate business
logic for shortcuts.

============================================================ 2. VISUAL
DESIGN SYSTEM
============================================================

DESIGN DIRECTION Use a premium, restrained, modern business-management
interface. The main visual identity is grayscale: off-white, charcoal,
black and neutral gray. Use color only when it communicates status,
category or an important action.

CORE PALETTE - App background: #F5F5F2 (warm off-white) - Main
surface/card: #FFFFFF - Primary text: #171717 (near black) - Secondary
text: #666666 - Muted text: #8A8A86 - Primary dark action: #222222 -
Dark surface: #303030 - Border/divider: #E5E5E1 - Subtle surface:
#EEEEEA - Disabled surface: #E8E8E4 - Disabled text: #A3A3A0

LIMITED SEMANTIC ACCENTS - Success: #287A52 - Warning / pending:
#A66A16 - Error / overdue: #B93838 - Information: #426B8A

Use semantic accents sparingly: status badges, validation, small chart
series, and alerts. Do not make the entire interface colorful. Keep
primary buttons charcoal/black with off-white text.

COLOR USAGE RULES - Use off-white for the overall page background. - Use
white for cards, forms and sheets. - Use near-black for headings,
primary text and main CTAs. - Use neutral gray for secondary labels,
metadata and dividers. - Use semantic colors only for meaningful
states. - Maintain readable contrast and accessible text sizes. - Never
communicate a status by color alone; include a label or icon.

TYPOGRAPHY Use one consistent family across the app, such as Inter or
the platform’s clean sans-serif fallback. - Page title: 22-24sp,
semibold. - Section heading: 16-18sp, semibold. - Card title: 14-16sp,
medium/semibold. - Body: 14sp. - Supporting label: 12sp. - Amounts:
20-26sp, semibold, tabular numerals where possible. - Form labels must
remain visible; do not rely on placeholder-only labels.

SPACING AND SHAPE - Base spacing unit: 4dp. - Typical page horizontal
padding: 16dp. - Section gap: 20-24dp. - Card padding: 14-16dp. - Input
height: approximately 50-54dp. - Button height: approximately 48-52dp. -
Card radius: 12-16dp. - Input radius: 10-12dp. - Use subtle borders
before heavy shadows. - Keep tap targets at least 44-48dp.

COMPONENT RULES Create reusable components for: - Primary, secondary,
text and destructive buttons. - Text, number, date, search and multiline
fields. - Dropdowns and searchable selectors. - Summary cards and list
cards. - Data rows and responsive tables. - Status badges. - App bars
and bottom navigation. - Filter chips and date-range selectors. -
Confirmation dialogs and bottom sheets. - Loading skeletons, empty
states and error states. - Success screens and receipt previews.

RESPONSIVE BEHAVIOUR Design for small Android phones first, then larger
phones and tablets. Prevent horizontal overflow. Long forms must scroll.
Keep important save/continue actions accessible without hiding fields.
Use safe areas and handle the Android keyboard correctly.

============================================================ 3.
TECHNOLOGY STACK
============================================================

MOBILE APPLICATION - Flutter: Android application framework. - Dart:
application language. - Material 3 foundations, customized through a
centralized ThemeData and design tokens. - State management: Riverpod
(recommended). - Navigation: go_router. - API client: Dio. - JSON
models: freezed and json_serializable, if the project team accepts code
generation. - Forms and validation: Form widgets with centralized
validators; optionally use a form package if it improves
maintainability. - Local key-value settings: shared_preferences. -
Secure tokens: flutter_secure_storage. - Local database/cache: Drift or
Isar only where offline/local querying is genuinely required. Do not
store authoritative financial balances only on-device. - PDF: pdf and
printing packages, with server-generated PDFs considered where
consistent business formatting is required. - File/image selection:
file_picker or image_picker as needed. - Charts: fl_chart or Syncfusion
Flutter Charts, subject to licensing and scope. - Notifications:
Firebase Cloud Messaging if push notifications are included.

IMPORTANT TAILWIND CLARIFICATION Tailwind CSS is not the styling engine
for a native Flutter screen. Flutter widgets do not use HTML/CSS
classes. For the Android app, implement the same design language using
Flutter ThemeData, ColorScheme, TextTheme, spacing constants and
reusable widgets.

Use Tailwind CSS only if a separate web dashboard/admin portal is built
using a web stack such as React or Next.js. If no web application is in
scope, do not add Tailwind to the Flutter codebase just to style mobile
screens.

ANIMATION FRAMEWORKS - flutter_animate: lightweight transitions for
Flutter widgets. - Lottie: branded loading or success animations where a
supplied/approved animation adds value. - Rive: interactive stateful
animations where genuinely needed. Use subtle animations only: 150-250ms
page transitions, small fade/slide entrances, button feedback and
loading states. Avoid continuous decorative animation, excessive motion
and animations that slow down data entry. Respect
reduced-motion/accessibility preferences where possible.

BACKEND Recommended implementation choice: - Node.js + Express.js -
TypeScript for backend maintainability - REST API over HTTPS -
PostgreSQL relational database - Prisma or Drizzle ORM (choose one and
standardize) - Zod or equivalent request validation - JWT access tokens
with refresh-token strategy, or a secure managed authentication
approach - Role-based authorization enforced on the server - Object
storage for uploaded receipts/logos if needed - Centralized logging and
error monitoring

The source specification allows a choice between Python or Node.js +
Express and MySQL or PostgreSQL. This plan recommends Node.js + Express
and PostgreSQL; confirm this stack before implementation.

INFRASTRUCTURE - Separate development, staging and production
environments. - HTTPS only. - Automated database backups. - Secrets
stored in environment variables/secret manager, never committed. -
Database migrations version-controlled. - API rate limiting and request
validation. - Audit logging for sensitive financial operations.

============================================================ 5.
PHASE-BY-PHASE IMPLEMENTATION PLAN
============================================================

RULE FOR EVERY PHASE Implement only the named phase. Inspect the
existing repository first. Reuse the approved design system. Do not
redesign unrelated screens. Do not use fake buttons or placeholder
business actions. Connect to real APIs when the backend is ready; until
then, use clearly isolated mock repositories that can be replaced
without rewriting the UI. Finish the phase’s acceptance checklist before
starting the next phase.

PHASE 0 — PROJECT AUDIT AND REQUIREMENTS FREEZE Tasks: 1. Inspect the
existing Flutter/backend repository. 2. Identify current pages, routes,
state management, models and APIs. 3. Review the approved feature
specification and current business rules. 4. Create a feature-to-page
traceability matrix. 5. Confirm terminology: Supplier and Customer. 6.
Confirm cash bill, credit bill, lot, payment and expense calculations
with the business owner. 7. Confirm whether the app is single-business
or multi-business. 8. Confirm authentication and user roles. 9. Record
out-of-scope items. Deliverables: - Existing codebase audit. - Approved
page inventory. - Business rules register. - Open questions register.
Exit gate: No financial formula or ambiguous business rule is silently
invented.

PHASE 1 — DESIGN SYSTEM AND APP FOUNDATION Tasks: 1. Create the
grayscale color tokens. 2. Create ThemeData, ColorScheme and TextTheme.
3. Create typography, spacing, radius and elevation tokens. 4. Build
reusable buttons, cards, inputs, selectors and badges. 5. Build app bar,
bottom navigation and dialogs. 6. Build loading, empty, error and
success patterns. 7. Set up app folder structure, linting and
environment configuration. 8. Add routing and state management
foundations. Pages/components: - Theme preview page (internal only). -
Reusable component showcase (internal only). Exit gate: Theme changes

PHASE 2 — AUTHENTICATION AND APP SHELL Pages: 1. Splash. 2. Login. 3.
Forgot/reset password or OTP flow only if approved. 4. Optional business

Handle expired sessions and logout. - Protect authenticated routes. -

============================================================ 6. REQUIRED
BUSINESS RULES AND CALCULATIONS
============================================================

Do not invent or hardcode accounting formulas until the business owner
approves them.

LOT AVAILABILITY Available quantity/weight must be derived from the
lot’s original amount less approved sales, returns and adjustments.
Decide whether stock is controlled by quantity, weight, both, or
product-specific rules.

OUTSTANDING BALANCE A proposed high-level relationship is: Opening
outstanding + credit transactions - allocated payments - approved
adjustments = current outstanding. Confirm whether cash bills can affect
outstanding and how advances are represented.

BILL TOTAL A proposed structure is: Line item totals + approved
labour/other charges - approved discounts = bill total. Confirm rate
basis, weight precision, rounding, taxes (if any) and charge allocation.

STOCK A proposed relationship is: Opening stock + incoming lots -
approved sales + approved returns +/- approved adjustments = closing
stock. Define units and treatment of cancelled bills.

PAYMENT ALLOCATION Define whether payment is allocated
oldest-bill-first, manually selected, to the current bill, or held as an
unallocated customer credit. Do not assume.

CANCELLATION Cancellation must: - Require permission. - Capture a
reason. - Preserve the original record. - Create traceable reversal
entries. - Reverse stock and ledger effects according to approved
rules. - Never hard-delete a financial transaction.

FINANCIAL DATA INTEGRITY - Use database transactions for
bill/payment/stock updates. - Use idempotency protection against double
taps and network retries. - Store money in integer minor units (for INR,
paise) or a suitable exact decimal type; never use floating-point
arithmetic for authoritative money calculations. - Store timestamps
consistently and display business-local dates. - Keep source references
for all ledger and stock movements. - Do not let the mobile app alone
determine authoritative balances.

DATA MODELLING RULES - Use immutable primary IDs. - Store

planned. - Add indexes for common searches: bill number, lot number,
phone, date, partner ID and status.

============================================================ 11.
IMPORTANT SCOPE NOTES
============================================================

The reference application specification identifies additional modules
such as Smart Chart/arrival/auction, separate bill books, partner
categories, ledgers, advances, stock summaries, expanded reports, RMC
reporting, mOS, wallet interfaces, customization and import/export.

These are not automatically included just because they appear in the
reference inventory. Confirm each module and its commercial/timeline
impact before implementation.

The earlier proposal material refers to Flutter Android, a choice of
backend (Python or Node.js + Express), a choice of database (MySQL or
PostgreSQL), REST APIs over HTTPS and WhatsApp setup subject to
access/configuration. This plan recommends Node.js + Express +
PostgreSQL but that is a recommendation to approve, not a claim that the
source documents mandated it.
